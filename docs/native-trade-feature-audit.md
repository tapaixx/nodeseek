核对日期：2026-11-23。原生基线：`v1.4.2-3`，提交 `4b732361ac5f2dfb3f3f790dbf45513367a18075`。

## 1. 证据范围

此次重新检查了官方站点 `https://agent.nodeseek.org/` 的页面路由、页面组件、接口调用和帮助内容。站点入口当前引用 `main-Q9nic8Aa.js`。组件文件名中的哈希只用于记录本次证据，不应写死为 App 依赖。

- **已确认的代码行为**：公开前端路由、组件中的显示条件、请求路径、请求字段、确认文案，以及本项目原生实现。
- **已登录实测**：用户在 OMacBook 的 Chrome 登录并开启 Apple 事件 JavaScript 后，已读取普通用户会话。检查了 13 个主页面、中介建群表单、托管发布表单、聊天筛选、新建交易和私聊表单、两条托管详情，以及一场公开交易的只读详情和消息字段结构。详见第 8 节。
- **尚未实际验证**：参与者自己的进行中交易、私聊、非空申请、积分资产状态、中介和管理员页面、真实业务写入和状态切换，以及大量数据的分页。不能将普通账号可见页面或模拟测试等同于这些场景已经验证。
- **浏览器检查方式**：最初遇到 AppleEvent 超时及 Chrome 禁用脚本执行；用户就绪并开启权限后，复用现有官方交易标签完成页面检查。接口通过站点自身 API 客户端调用，只导出字段名、类型、数量和必要的权限标志，未导出凭证。检查结束后恢复到原先的 `/trade/calculator` 页面。
- 没有重新触发 connect，没有读取 Cookie 或登录令牌，没有发布托管、邀请他人、发送消息、评价、领取红包或执行资金和货物操作。

前期实现依据公开脚本和模拟接口，主要完成了聊天内交易，未按完整站点建立功能基线。缺少实际登录页面核对是验证缺口；遗漏交易大厅也与需求拆分不完整有关，不能单纯归因于“登录后不可见”。

## 4. 聊天和交易仍缺的能力

1. **创建方式**：网页支持暂不选具体中介、通知所有可通知中介、按用户名向对方申请组建交易并选择双方身份。原生只支持选择一个具体中介后创建交易。
2. **私聊和申请**：发出、收到、同意、拒绝、撤回、已结束记录，以及同一用户多场私聊和关联交易。证据：`/api/common/private/requests`、`/private/sessions`、`RequestRoom-DicwVYXm.js` 和 `Requests--TJmiDnV.js`。
3. **消息权限**：普通公开内容、定向私密内容、隐藏内容、删除记录、图片、引用、表情、编辑及历史、置顶和权限内公开聊天。现有消息模型没有完整表达这些状态，不能把隐藏消息渲染成普通空消息，也不能把群内隐私提示省掉。
4. **风险与费用**：交易内风险提示、按中介规则计算费用、买家应付／卖家实收、外币换算及汇率说明、品牌和交货方式编辑。
5. **流程管理**：申请解锁、三方重置／关闭流程辅助的提出、同意、拒绝与撤回；取消／退出交易、更换身份、旁观者管理、交易结束评价。原生实现了部分确认及推进，未形成完整闭环。
6. **不同交易模式**：普通交易、托管交易和中介口令红包各有不同的条款编辑、自动确认、放货、取消及资金规则，不能共用一套不分模式的按钮。
7. **实时状态**：官方使用实时事件更新会话、权限、进度、申请和积分。原生目前主要轮询交易详情，仍需核对会话列表刷新、未读和重新连接后的补偿行为。

消息菜单与权限证据来自 `RoomView-CItalcWf.js`；申请与创建证据来自 `HallLayout-DQylLxGr.js`；模式差异与隐私规则由 `/docs/modes`、`/docs/chat`、`/docs/trust` 和 FAQ 的公开组件交叉核对。

## 5. 用户面板及特殊角色

- 概览：成功交易、累计金额、进行中会话、待处理申请；`GET /api/common/me/stats`。
- 个人资料：交易平台内简介和建群链接；`PATCH /api/common/me`。
- Telegram：绑定状态、绑定入口及解绑；`/api/common/telegram`。这是通知接入，不应在本次分析中触发绑定或发送消息。
- 快捷消息：维护常用话术，选中后只填入输入框，须用户再发送；`/api/common/quick-messages`。
- 积分：按发行中介区分余额、明细、充值订单、兑换、中介口令红包、提现确认等；`/api/common/points...`。涉及真实资产，需要单独核对金额、状态和不可逆节点。
- API Key：供公开数据查询的只读 Key，不是 App 私人账号登录替代品；`/api/common/api-keys`。分析不需要创建或获取 Key。
- 中介／管理面板：须用对应角色检查，普通用户登录不能代表这些功能已验证。路由和面板脚本加载机制与普通页面不同，待单独核对。

## 6. 建议的原生结构与实施顺序

交易模块内采用“大厅／聊天／我的”三个明确入口，保留当前 App 阅读模式和多 Tab 模式的入口方式。用户打开交易系统应能立即发现大厅，而不是先进入个人交易列表。

1. **先补大厅和交易前判断**：中介完整卡片及详情、托管大厅与详情、交易查询和风险查询、公开记录。复用现有会话和网络层，补真实响应模型。
2. **再补交易建立闭环**：托管发布、指定／不指定中介、建群和私聊申请、申请处理、角色相关的托管操作。公开详情与货物信息必须分开输入和展示；查看货物时需尊重服务端审计行为。
3. **完善聊天与善后**：私密消息、图片、快捷话术、置顶、评价、取消／退出和三方申请；每项操作按真实权限展示。
4. **补工具与账户功能**：品牌统计、计算器、反馈、个人资料和 Telegram 设置。
5. **积分与中介业务单独完成**：先只读账户状态，再验证业务允许的写入；中介／管理员入口按角色分开。不要在没有真实角色证据时把所有入口展示给普通用户。

## 7. 登录后页面的核对方式

需要一个用户已登录且可读取的官方交易站页面。优先复用现有交易会话，不反复调用 connect。可在保持登录的浏览器内查看 DOM、页面截图和只读请求的结构；不得将 Cookie、令牌、私密消息或货物信息写入项目文档。

首轮按以下路线核对，记录“角色、入口、列表状态、可用操作、响应结构和原生差距”：

1. 交易大厅全部导航，中介目录及中介详情。
2. 托管大厅／与我有关，详情、发布表单和不同状态的入口。只打开表单，不提交；不点击查看货物。
3. 交易查询、风险查询表单、品牌统计、公开聊天和计算器。避免为验证主动查询不相关账号。
4. 聊天列表、新建表单、申请、已有交易详情和消息菜单。先确认点击是否会发出邀请或改变状态。
5. 用户面板导航、快捷消息、通知设置和账户只读信息。避免领取、支付、兑换、绑定和创建 Key。

没有对应状态的真实数据时明确记为未验证，不通过创建真实订单填补测试数据。后续以脱敏响应或模拟数据验证写入状态机，再按用户明确选择的业务执行真实写入。

### 8.2 真实响应与建模要求

1. `GET /api/auth/me` 确认当前 `user.role == "user"`。普通用户导航没有“等待交易”和中介／管理面板，不应为这些入口伪造可用权限。
2. 中介资料除基本身份外，含 `completed`、`reputation` 和 `profile`。`reputation` 中有 `score`、`reviews`、`user_score`、`user_reviews` 及中介取消率／响应时间；`profile` 中有在线状态、时间段、`online_auto`、费率／最低／封顶及补充介绍。费率和金额有字符串，部分数值为 null，需要保留“未设置”和零值的区别。
3. 托管列表响应为 `{tasks: [...]}`；详情为 `{task: {...}}`。公开条款外，详情还返回 `can_accept`、`can_decline`、`can_reassign`、`can_view_goods`、`can_open_chat`、`can_cancel`，以及风险、关联群聊等字段。权限应以详情字段为准，列表不代表拥有写入资格。
4. 品牌统计响应为 `totals`、`series`、`hot`；本次 `series` 包含 30 个日期点，`hot` 为空。金额和均价为字符串，日成功笔数为数字。
5. 公开记录列表复用 conversation 结构，包含类型、状态、`is_public`、最近消息、参与者及交易摘要。详情中 `access.role` 为 null，`can_write`、`can_moderate`、`can_delete_others`、`can_pin` 全部为 false。能查看公开记录不等于旁观者入座，更不等于参与交易。
6. 公开交易详情中的价格、中介费之外，还有 `settlement.buyer_fee`、`seller_fee`、`buyer_pays`、`seller_gets` 和费用解释；`fee_policy` 含中介费率规则。原生确认付款／放款前应展示对应的应付与实收，不能只有物品价格。
7. 实际进度步骤含 `key`、`label`、`roles`，与此前脚本分析一致。交易还有重置、解锁、提案、托管来源、红包等状态，必须按模式解释。
8. 消息响应包含 `meta`、`image_url`、`edit_count`、`edited_at`、`edits_visible`、`pinned_at`、`visible_to`、`reactions`、`reply_to`、`quote_text`。本次仅导出字段结构，未保存聊天正文。当前原生模型忽略多项权限及消息语义字段，需要在添加私密消息或图片时一并补齐。
